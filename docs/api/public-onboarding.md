# Public onboarding API

M6C2B2 adds an invitation-only backend flow. `GET /api/v1/onboarding/config` is always registered; when disabled it returns `enabled: false`, an empty role list, and a request ID. Every other route is absent (`404`) unless the local, test, or demo feature gate is enabled with the injected fake provider and a complete approved legal-document set.

Enabled endpoints are `GET /onboarding/consents?locale=ar|en`, `POST /onboarding/attempts`, `POST /onboarding/attempts/:id/resend`, `POST /onboarding/attempts/:id/verify`, `POST /onboarding/attempts/:id/complete`, `GET /onboarding/status`, and `POST /onboarding/status-sessions`, all under `/api/v1`. Mutation routes require the documented `Idempotency-Key`; attempt-bound routes require `Authorization: Onboarding <opaque-token>`. Bearer JWTs and onboarding credentials are intentionally not interchangeable.

Start accepts an invitation code, immutable role, phone, explicit `PS` region, and locale. Darb sends no SMS: the one-time code is emailed to the invitation's contact email, or, for open driver/shop sign-up (no invitation code), to the `email` the applicant supplies in this first step (`email` is required without an invitation code and rejected with one). With `OTP_PROVIDER=email` the phone of an open sign-up stays unverified (see `docs/security/email-codes-instead-of-sms.md`). Equivalent retries resume the one existing attempt without another send and rotate the continuation token. Verification returns a one-time registration grant. Completion accepts the grant, display name, password, locale, exactly the current three consent IDs/hashes, and explicit adult self-attestation.

Passenger completion creates an active account but no auth or refresh session and directs the client to normal login. Driver and merchant completion creates a pending account and returns only a narrow pending-status token. Safe errors use stable codes and always include `request_id`; invitation/account/provider details, raw phone, OTP, password, hashes, and internal state are never returned.

## Direct sign-up without a code (`ONBOARDING_CODE_DISABLED`)

When the host cannot send email, the owner can set `ONBOARDING_CODE_DISABLED=true` (in staging and production also `ALLOW_UNVERIFIED_ONBOARDING=true`, plus `EMAIL_VERIFICATION_DISABLED=true` so an approved applicant can sign in). Then `POST /onboarding/attempts` returns `status: "phone_verified"`, `next_action: "complete_registration"` and the `registration_grant` straight away; `/verify` and `/resend` answer 404, and `GET /onboarding/config` reports `code_required: false`. Every other guard stays: start rate limits per IP, phone and email, the hourly total, idempotency, one live attempt per phone, the consent check, the duplicate phone/email check at completion, documents and Admin approval. The account is stored with `email_verified_at` and `phone_verified_at` empty, and Admin user and driver review responses carry `contact_unverified: true` for it.
